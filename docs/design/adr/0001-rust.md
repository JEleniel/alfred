# ADR 0001: Rust Implementation Language

## Status

Accepted

## Context

Alfred is a local MCP server that runs as a single stdio process on developer machines (macOS, Linux, Windows). It provides performance-sensitive primitives (indexing, search, diff/patch, streaming job output) while enforcing strict safety boundaries (workspace-only file access, dry-run behavior, deterministic error contracts).

This combination places a premium on:

- Predictable performance for typical repositories and bounded overhead for large files
- Memory safety and robust concurrency for background operations and streaming output
- Flexibility to build a modular tool surface with clean interfaces and testability
- Cross-platform distribution without relying on external services

## Decision

Implement Alfred in Rust.

## Rationale

Rust was selected because it best satisfies Alfred’s primary constraints:

- Performance: Rust enables low-overhead IO, efficient indexing/search pipelines, and predictable latency without requiring a VM.
- Safety: Rust’s ownership model and type system provide strong memory-safety guarantees and help prevent common classes of concurrency bugs.
- Flexibility: Rust supports modular architectures (libraries/crates, traits, strong typing) that map well to Alfred’s componentized tool surface and deterministic contracts.
- Cross-platform usability: Rust supports building and distributing native executables across macOS/Linux/Windows, matching Alfred’s local-first stdio deployment model.

## Alternatives Considered

- Go: strong concurrency story and portability, but less expressive type system for some invariant-heavy contracts; performance is good but fine-grained control over allocations and lifetimes is less explicit.
- Node.js/TypeScript: excellent ecosystem for tooling, but runtime overhead and memory characteristics are less ideal for indexing/search workloads and large-file operations; packaging as a single native binary is less straightforward.
- Python: rapid development, but performance and packaging for a long-running, concurrency-heavy stdio server are higher-risk.

## Consequences

- Positive:
    - Better default safety posture for long-lived processes that handle untrusted inputs and complex file operations
    - Strong performance baseline for indexing/search/diff and for streaming background job outputs
    - Good fit for cross-platform local distribution

- Negative:
    - Higher implementation complexity than dynamic languages for some features
    - Dependency selection and compile times require deliberate project hygiene
